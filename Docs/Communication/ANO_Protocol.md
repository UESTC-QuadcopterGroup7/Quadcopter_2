# 匿名上位机通信：ANO 模块

本文说明本项目新增的 `MyLib/ANO.c` / `MyLib/ANO.h`：为什么要发二进制帧、帧长什么样、每个字段的单位、
三条飞控帧分别喂给上位机的哪些通道、`ReadPeripherals.c` 怎么调用、以及现在还没做什么。

本文只描述当前源码状态，参数是按公开资料与实测现象估的，不代表已逐字节对照官方手册验证。

## 1. 为什么需要这个模块

最初的串口输出是 `printf` 风格的文本：

```text
MPU A:-123,45,16384 G:12,-8,3
HMC M:120,-340,560
ATT R:1.23 P:-0.45 Y:87.60
```

人眼可直接读，但匿名上位机不认识。它以「同步头 + 长度 + 校验」在字节流里找帧，
文本没有同步头也没有长度字段，于是每个字节都被判为错误——上位机底部显示 `错误码率 100.0000%`，
波形和 3D 模型全是 0。

`ANO.c` 的职责就是把这些数值封装成上位机认识的二进制帧：

```text
0xAA | 目标地址 | 功能码 | 数据长度 | 数据... | 和校验 | 附加校验
```

### 1.1 文件与依赖

| 文件 | 作用 |
|---|---|
| [MyLib/ANO.h](../MyLib/ANO.h) | 协议说明、定点比例宏、对外接口 |
| [MyLib/ANO.c](../MyLib/ANO.c) | 组帧、校验、量化，并通过 `huart1` 发送 |
| [MyLib/ReadPeripherals.c](../MyLib/ReadPeripherals.c) | 在通信任务里换算物理量并按节拍调用 ANO 接口 |
| [LED.uvprojx](../LED.uvprojx) | 在 `MyLib` 分组中登记 `ANO.c` / `ANO.h` |

依赖方向是单向的：`ANO.c` 只依赖 `main.h`（HAL）和 `UART_Set.h`（取 `huart1`），
不认识任何传感器。`ReadPeripherals.c` 调用它，它不回调上层。

## 2. 帧格式

### 2.1 字段

| 偏移 | 字段 | 长度 | 说明 |
|---|---|---|---|
| 0 | 帧头 | 1 | 固定 `0xAA` |
| 1 | 目标地址 | 1 | `0xFF` = 广播（`ANO_TARGET_ADDR`） |
| 2 | 功能码 | 1 | 决定这包数据归谁用，见第 3 节 |
| 3 | 数据长度 | 1 | **字节数**，不是元素个数 |
| 4 | 数据 | LEN | 小端，见 2.3 |
| 4+LEN | 和校验 | 1 | 见 2.2 |
| 5+LEN | 附加校验 | 1 | 见 2.2 |

整帧长度 = `6 + LEN`。

### 2.2 两种校验

```c
uint8_t sum = 0, add = 0;
for (i = 0; i < 4 + LEN; i++) {      /* 从 0xAA 一直到最后一个数据字节 */
    sum = (uint8_t)(sum + buf[i]);
    add = (uint8_t)(add + sum);
}
```

- **和校验 `SUM`**：逐字节累加取低 8 位，能发现单字节错误；
- **附加校验 `ADD`**：每加一个字节，就把当前的 `SUM` 也累加一次。它专门抓「相邻两字节对调」
  这类和校验看不出来的错误——对调后 `SUM` 不变，`ADD` 一定变。

两个校验的值都不参与自身的计算，只覆盖 `0xAA` 到数据末字节。

### 2.3 字节序

全部小端。STM32 本身就是小端，所以浮点可以直接按字节搬，不用手工拆位；
`ANO_SendInt16s()` 里也显式按「低字节在前」拆，避免依赖编译器。

### 2.4 一个可手算的例子

姿态 `roll = +10.00°`、`pitch = -5.00°`、`yaw = +90.00°`，比例 0.01°/LSB：

| 数值 | int16 | 小端字节 |
|---|---|---|
| +10.00° → 1000 | `0x03E8` | `E8 03` |
| -5.00° → -500 | `0xFE0C` | `0C FE` |
| +90.00° → 9000 | `0x2328` | `28 23` |

```
AA FF 03 06 E8 03 0C FE 28 23 F2 F9
│  │  │  │  └──────┬──────┘  │  │
│  │  │  │         │         │  └─ ADD = 0xF9
│  │  │  │         │         └──── SUM = 0xF2
│  │  │  │         └────────────── 3 × int16 = 6 字节
│  │  │  └──────────────────────── LEN = 6
│  │  └─────────────────────────── 功能码 0x03（姿态）
│  └────────────────────────────── 目标地址 0xFF
└───────────────────────────────── 帧头 0xAA
```

调试时截一帧下来，用这张表逐字节对，比看代码快。

## 3. 发送的三条帧

功能码 `0x01 / 0x02 / 0x03` 是**飞控固定帧**，字段顺序和单位由协议写死，
对应上位机「波形显示」里 `FC_ACC_*`、`FC_GYR_*`、`FC_MAG_*`、`FC_ATT_*` 那些通道名。
「飞控状态」页的 3D 模型、罗盘、`ROL/PIT/YAW` 也吃这几帧。

| 功能码 | 长度 | 频率 | 字段（顺序固定） | 上位机通道 |
|---|---|---|---|---|
| `0x01` | 14 | 50 Hz | acc_x, acc_y, acc_z, gyr_x, gyr_y, gyr_z, shock | `FC_ACC_X/Y/Z`、`FC_GYR_X/Y/Z`、`FC_STA_Shock` |
| `0x02` | 14 | 25 Hz | mag_x, mag_y, mag_z, alt, temp, sta_bar, sta_mag | `FC_MAG_X/Y/Z`、`FC_ALT_BAR`、`FC_SensorTMP`、`FC_STA_BAR/MAG` |
| `0x03` | 6 | 50 Hz | roll, pitch, yaw | `FC_ATT_ROL/PIT/YAW` |

单位换算集中在 [ANO.h](../MyLib/ANO.h) 的三个宏里：

| 宏 | 值 | 含义 |
|---|---|---|
| `ANO_LSB_ACC` | 100.0 | 0.01 m/s² / LSB |
| `ANO_LSB_GYR` | 10.0 | 0.1 °/s / LSB |
| `ANO_LSB_ATT` | 100.0 | 0.01 ° / LSB |

显示值整体差 10 倍或 100 倍时，只改这三个数，不要动结构。

`0x02` 里的高度、温度当前恒为 0——气压计 `MS5611` 的采集在 `ReadPeripherals.c` 里是 `#if 0` 停用状态。
`sta_mag` 用 `g_HmcAddressAck == 0` 判断磁力计是否在线（0 表示应答，即在线）。

## 4. API

### 4.1 对外接口

| 函数 | 说明 |
|---|---|
| `ANO_SendInt16s(fun, values, count)` | 把 `count` 个 int16 小端打包成 `fun` 帧，`count ≤ 10` |
| `ANO_SendFloats(fun, values, count)` | 同上，float 版本；当前未被调用，留给 `0xF1` 用户帧 |
| `ANO_SendFC_AccGyr(acc_m_s2[3], gyr_dps[3], shock)` | 组 `0x01` 帧，内部完成物理量 → 定点 |
| `ANO_SendFC_MagBaro(mag[3], alt_m, temp_c, sta_bar, sta_mag)` | 组 `0x02` 帧 |
| `ANO_SendFC_Attitude(roll_deg, pitch_deg, yaw_deg)` | 组 `0x03` 帧 |

三条 `ANO_SendFC_*` 是给调用方省事的糖：上层只负责把原始计数换成物理量，
定点化、限幅、组帧、校验都留在协议层。

### 4.2 内部实现

```text
ANO_SendFC_Attitude(roll, pitch, yaw)
        │  ANO_Quantize(角度, ANO_LSB_ATT)   ← 四舍五入 + 饱和到 int16
        ▼
ANO_SendInt16s(0x03, v, 3)                  ← 打包小端
        ▼
ANO_SendPacket(fun, payload, len)           ← 加帧头/长度/两种校验
        ▼
HAL_UART_Transmit(&huart1, ...)             ← 阻塞发送，超时 100 ms
```

`ANO_Quantize()` 先乘比例再四舍五入，最后饱和到 `[-32768, 32767]`。
饱和是必要的：陀螺仪 ±2000 °/s 换算成 0.1 °/s 后是 ±20000，超出 int16 时如果不限幅会直接翻转成负值。

## 5. 数据流与节拍

```text
GY-86(I2C) ──► ReadPeripherals_Process() ──► g_MPU6050 / g_HMC5883L
                        │                    g_Attitude（Madgwick 四元数 → 欧拉角）
                        └──────────────┐
                                       ▼
                    ReadPeripherals_Transmit()（每 10 ms 一次）
                        │
                        ├─ 每拍     → 0x03（100 Hz，姿态，最先发）
                        ├─ 每 2 拍  → 0x01（50 Hz，加速度/角速度）
                        └─ 每 4 拍  → 0x02（25 Hz，磁力/气压）
                                       │
                                  UART1 115200
                                       ▼
                              匿名上位机 V7
```

发帧不依赖 `att.fresh`：传感器一上电就开始发 `0x01`，姿态有效后才追加 `0x03`。
这样即使姿态初始化失败，串口也不会整条静默——便于区分「没发」和「没解析」。

### 5.1 带宽

| 项 | 计算 | 结果 |
|---|---|---|
| `0x03` | 12 B × 100 | 1200 B/s |
| `0x01` | 20 B × 50 | 1000 B/s |
| `0x02` | 20 B × 25 | 500 B/s |
| 合计 | | ≈ 2.7 kB/s |

115200 8N1 的可用带宽约 11.5 kB/s，占用约 23%。

每个 `HAL_UART_Transmit` 都是阻塞的。每拍先发 `0x03`（12 B ≈ 1.0 ms），
每隔一拍追加 `0x01`（20 B ≈ 1.7 ms），每隔四拍追加 `0x02`（20 B ≈ 1.7 ms），
最坏一拍合计约 4.5 ms，仍在 10 ms 周期之内。姿态帧排在最前面，是为了不让加速度帧
把姿态数据的发出时刻往后推。

### 5.2 端到端延迟

从传感器到屏幕要经过五段，逐段估算：

| 环节 | 改动前 | 改动后 | 依据 |
|---|---|---|---|
| MPU 数字低通群延迟 | ~2.9 ms | ~1.9 ms | `CONFIG` 0x02 → 0x01（94 → 184 Hz） |
| 采样周期（取半周期计） | 5 ms | 2.5 ms | `SMPLRT_DIV` 9 → 4（100 → 200 Hz） |
| 一次 I2C 读数 | ~17 ms | ~1 ms | 12 次事务 → 1 次突发读；半周期 10 µs → 2 µs |
| 采样循环总周期 | ~26 ms | ~2 ms | 上述两项 + 1 ms 任务延时 + 1/4 频的磁力计读 |
| 串口发送（取半周期计） | 10 ms | 5 ms | 姿态帧 50 → 100 Hz |
| 蓝牙 SPP 链路 | 20~40 ms | 20~40 ms | HC-05 固有，固件无法改善 |
| 上位机渲染 | 16~33 ms | 16~33 ms | 30/60 fps 重绘 |

合计约 **90~120 ms → 40~60 ms**。剩下的两大块（蓝牙、渲染）都不在固件里：
换 USB-TTL 直连可以再去掉 20~40 ms，而渲染帧率由上位机决定。

逐段的推导、算式和取舍见 [Latency_Optimization.md](../Performance/Latency_Optimization.md)。

注意 `dt` 的计算也跟着改了：采样周期降到 2 ms 以后，`HAL_GetTick()` 的 1 ms 分辨率
会带来 25% 的误差，所以改用 DWT 周期计数器（84 MHz）直接换算秒。

为降低延迟一并修改的文件（不属于 ANO 模块，但决定这条链路的时序）：

| 文件 | 改动 |
|---|---|
| [MyLib/Delay.c](../MyLib/Delay.c) | TIM5 改为自由运行，去掉每次调用 `Start`/`Stop` 的开销 |
| [MyLib/MyI2C.c](../MyLib/MyI2C.c) | 半周期 10 µs → 2 µs（约 50 kHz → 150 kHz） |
| [MyLib/GY86.c](../MyLib/GY86.c) | 突发读（MPU 14 字节、HMC 6 字节一次读完）、200 Hz 采样、184 Hz 低通 |

## 6. 可调参数

| 位置 | 宏 | 默认 | 作用 |
|---|---|---|---|
| [ANO.c](../MyLib/ANO.c) | `ANO_TARGET_ADDR` | `0xFF` | 目标地址；个别固件版本认 `0xAF`，改这一行即可 |
| [ReadPeripherals.c](../MyLib/ReadPeripherals.c) | `ANO_TICK_DIV` | 1 | 每 N 拍发一帧姿态；1 → 100 Hz |
| [ANO.h](../MyLib/ANO.h) | `ANO_LSB_ACC/GYR/ATT` | 100/10/100 | 定点比例 |

文本行（`MPU` / `HMC` / `ATT`）目前整体包在 `#if 0` 里，不再发送，
所以 `错误码率` 应当稳定在 `0.0000%`。需要临时看文本时，把那一块改成 `#if 1` 即可，
但错误码率会随之回升——它统计的是「非帧字节 / 总字节」。

## 7. 调试

### 7.1 三个数字怎么读

| 现象 | 含义 | 处理 |
|---|---|---|
| `接收计数` 不涨 | 链路没通（波特率、接线、蓝牙占用） | 查物理层，与协议无关 |
| `接收计数` 涨、`错误码率` 100% | 一帧都没解析出来 | 查帧头/长度/地址，或数据类型是否对 |
| `错误码率` 明显不为 0 | 有非帧字节混在流里（文本输出被打开了） | 关掉文本，或将帧长/地址对齐 |
| 波形全 0 但计数在涨 | 帧发的不是这个通道集 | 确认功能码与通道名对应 |

### 7.2 常见故障

| 现象 | 可能原因 |
|---|---|
| 3D 不动、`ROL/PIT/YAW` 恒 0 | `0x03` 没发：姿态从未初始化（`att.fresh == 0`） |
| 平放时角度稳定偏几度 | 上电校准那一刻板子没放平，或 IMU 安装面与机架不平行 |
| 角度缓慢漂移 | 陀螺零偏未完全收敛，属正常；可提高 `beta` 或延长静置校准 |
| 倾斜时 `YAW` 跟着乱跳 | HMC5883L 与 MPU6050 轴向不一致，需调整轴序或符号 |
| 改完没反应 | Keil 里 `ANO.c` 没进工程，或烧的是旧固件 |

## 8. 已知限制

1. **只发不收**。`UART1_FULL_INIT` 没有开启接收中断，全工程也没有 `USART1_IRQHandler`，
   所以上位机下发的参数读取、功能触发命令一律收不到，界面必然出现
   `等待校验数据超时，重试 1..5` → `参数读取失败`。这不影响波形和 3D。
2. **气压计与电压帧未实现**。`FC_ALT_BAR`、`FC_SensorTMP` 以及“飞控状态”页的电压恒为 0。
3. **帧字段按公开资料实现**，未逐字节对照官方手册；若某帧被整帧丢弃，
   优先怀疑「长度」或「int16 / float」选错，改 `ANO_SendFC_*` 的打包方式即可。
4. **未做发送队列**。三个帧都走阻塞发送，若将来加高频率帧，需要评估通信任务的最坏执行时间。

## 9. 扩展：再加一条帧

1. 在 `ANO.h` 里声明 `void ANO_SendFC_XXX(...)`，写清单位；
2. 在 `ANO.c` 里用 `ANO_Quantize()` 定点化，再调 `ANO_SendInt16s(功能码, v, n)`；
3. 在 `ReadPeripherals_Transmit()` 里按需要的分频调用；
4. 通道数受 `ANO_MAX_CHANNELS`（当前 10）限制：int16 帧最多 20 字节数据，
   float 帧最多 40 字节。超限时 `ANO_SendInt16s()` / `ANO_SendFloats()` 直接返回，
   `ANO_SendPacket()` 也会丢弃超长帧——加了帧却收不到时，先看这里。
