# 姿态链路的延迟分析与优化

匿名上位机里 3D 模型的跟随明显“慢半拍”。本文把这段延迟拆成可计算的几段，
说明每一段的量级、这次改了哪些地方、改动背后的算式和代价，以及还剩什么没法在固件里解决。

文中数据是按时序推算的估算值，用于比较前后量级，不是示波器实测结果；
最后一节给出了把它测准的方法。

## 1. 延迟从哪来

从“板子转动”到“屏幕上的模型转动”，中间是一串串联环节，每一段都在加延迟：

```text
物理转动
   │
   ├─① 传感器滤波      DLPF 群延迟
   ├─② 采样等待        输出数据率决定，平均半个周期
   ├─③ I2C 读取        软件模拟 I2C 的时序
   ├─④ 任务调度        OSTimeDly 的节拍 + 抢占
   ├─⑤ 串口排队        一帧多少字节 / 多少 Hz
   ├─⑥ 链路传输        蓝牙 / USB 串口
   └─⑦ 上位机渲染      30 或 60 fps 重绘
        ▼
      屏幕更新
```

总延迟近似为各段之和（都是正延迟，不能相互抵消）：

```text
T ≈ T_dlpf + T_odr/2 + T_i2c + T_sched + T_uart/2 + T_link + T_render
```

改造前逐项代进去，T 约 **90~120 ms**，人眼完全能察觉。

## 2. 改造前的现象与推断

三个现象把瓶颈指得很清楚：

| 现象 | 推论 |
|---|---|
| 一次采样循环要“顿”一下才出数 | ③ I2C 是瓶颈 |
| 按字节数与波特率推算，采样循环约 26 ms（≈38 Hz） | 采样率被 I2C 拖垮，不是 MPU 的上限 |
| 晃动时角度跟得上、但画面整体滞后 | ⑤⑥ 串口与蓝牙在叠加 |

其中 ③ 是最反常的一段：**读一次 MPU6050 要十几毫秒**，比传感器本身的采样周期还长。

## 3. 六个动作

### 3.1 延时函数：从“每次重启定时器”到自由运行

原实现（[Delay.c](../../MyLib/Delay.c)）每次调用都做一遍：

```c
__HAL_TIM_SET_COUNTER(&htim5, 0);
HAL_TIM_Base_Start(&htim5);
while (__HAL_TIM_GET_COUNTER(&htim5) < xus) { }
HAL_TIM_Base_Stop(&htim5);
```

`HAL_TIM_Base_Start/Stop` 要写 CR1、检查状态，光这一对调用的开销就接近 10 µs，
而请求的延时本身只有 10 µs——**开销和有效时间一样大**。

改成：TIM5 只初始化一次并一直自由运行，延时只比较计数器差值。

```c
start = __HAL_TIM_GET_COUNTER(&htim5);
while ((__HAL_TIM_GET_COUNTER(&htim5) - start) < xus) { }
```

32 位自由运行的计数器会回绕（84 MHz 下约 51 s 一次），无符号减法天然处理回绕，
不需要额外判断。单次开销从 ~10 µs 降到几百 ns。

### 3.2 软件 I2C 的时序：半周期 10 µs → 2 µs

软件 I2C 的每一位由三次电平变化组成（写数据、拉高时钟、拉低时钟），
每次变化后面跟一个半周期延时：

```text
t_bit ≈ 3 × (t_delay + t_gpio)
```

| 项 | 改造前 | 改造后 |
|---|---|---|
| 半周期延时 | 10 µs | 2 µs |
| 单次电平变化（含 GPIO 与函数开销） | ~13 µs | ~2.3 µs |
| 单 bit | ~40 µs | ~7 µs |
| 等效 SCL | ~25 kHz | ~150 kHz |

150 kHz 对 GY-86 是安全的：MPU6050 与 HMC5883L 都支持 400 kHz，
模块自带 4.7 kΩ 上拉，短线束的上升沿在 0.3 µs 量级。

### 3.3 突发读：事务数 18 → 2

原实现每读一个寄存器都要独立起一次事务（Start → 地址 → 寄存器 → Restart → 读一字节），
MPU6050 需要 12 次、HMC5883L 需要 6 次。

两颗芯片都支持寄存器地址自增，可以从首地址一次读出连续区间：

| 芯片 | 区间 | 字节数 | 事务数（前 → 后） |
|---|---|---|---|
| MPU6050 | `0x3B`~`0x48` | 14（加速度 6 + 温度 2 + 陀螺 6） | 12 → 1 |
| HMC5883L | `0x03`~`0x08` | 6（X、Z、Y 各 2） | 6 → 1 |

时间账（半周期 2 µs）：

```text
一次事务 = (地址 9 bit + 寄存器 9 bit + 地址 9 bit + 数据 8 bit × N + 起停)
17 字节 ≈ 163 bit × 7 µs ≈ 1.1 ms
```

改造前：`12 × 1.4 ms ≈ 17 ms`（MPU）+ `6 × 1.4 ms ≈ 8 ms`（HMC），合计约 25 ms。
改造后：`1.1 ms`（MPU）+ `0.5 ms × 1/4`（HMC 降频），合计约 1.2 ms。

**一个容易踩的坑**：HMC5883L 的输出顺序是 **X、Z、Y**，不是 X、Y、Z。
突发读按地址连续取，必须按它的原生顺序拆，否则 Y/Z 会互换。

### 3.4 传感器配置：输出率与低通

MPU6050 的两个寄存器直接决定延迟：

| 寄存器 | 作用 | 改造前 | 改造后 | 延迟变化 |
|---|---|---|---|---|
| `SMPLRT_DIV` | 输出数据率 = 1 kHz / (1 + DIV) | 9 → 100 Hz | 4 → 200 Hz | 采样等待 5 ms → 2.5 ms |
| `CONFIG` | 数字低通带宽（群延迟随之变化） | 0x02 → 94 Hz, ~2.9 ms | 0x01 → 184 Hz, ~1.9 ms | 1 ms |

采样等待取半个周期：100 Hz 时平均要等 5 ms 才拿到下一份新数据，
而 I2C 读取本身只要 1 ms——**等数据比读数据还久**，这是第二个瓶颈。

这就是 3.3 和 3.4 必须一起做的原因：只提速 I2C 而不提高输出率，
读到的还是同一份旧数据。

### 3.5 发送节拍与顺序

轮询式发送（没有 DMA、没有发送队列）时，一帧的发完时刻 = 前面所有字节的传输时间之和。
因此有两件事必须做：

**节拍**：姿态帧从 50 Hz 提到 100 Hz。平均发送延迟从 10 ms 降到 5 ms。
每帧 12 字节，115200 8N1 下约 1.0 ms，10 ms 周期内完全放得下。

**顺序**：把姿态帧放在同一拍的最前面。

```c
/* 先发 0x03，再发 0x01，最后按 1/4 频发 0x02 */
ANO_SendFC_Attitude(...);              // 12 B ≈ 1.0 ms
if (++s_motion_div >= 2) { ANO_SendFC_AccGyr(...); }   // 20 B ≈ 1.7 ms
if (++s_env_div >= 4)    { ANO_SendFC_MagBaro(...); }  // 20 B ≈ 1.7 ms
```

原先把 20 字节的加速度帧排在姿态帧前面，等于凭空给姿态加了 1.7 ms 排队时间。
顺序调整不花任何代价，纯赚。

带宽核算：`12×100 + 20×50 + 20×25 ≈ 2.7 kB/s`，占 115200 可用带宽的 23%。
再往上提频率收益就很小了——115200 下每增加 1 ms 的发送量，就多 1 ms 排队。

### 3.6 dt 的精度：HAL_GetTick → DWT

Madgwick 用 `dt` 把陀螺角速度积分成角度，`dt` 的误差会直接变成角度误差。

采样周期降到 ~2 ms 以后，`HAL_GetTick()` 的 1 ms 分辨率意味着最多 50% 的相对误差，
积分结果会明显抖动。改用 Cortex-M4 的 DWT 周期计数器：

```c
CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;
DWT->CYCCNT = 0;
DWT->CTRL |= DWT_CTRL_CYCCNTENA_Msk;

dt = (float)(uint32_t)(now_cyc - last_cyc) / (float)SystemCoreClock;
```

84 MHz 下分辨率约 12 ns，远超需要。计数器 51 s 回绕，无符号减法处理，
前提是两次采样间隔远小于 51 s（实际 2 ms，安全余量极大）。

## 4. 改造前后对照

| 环节 | 改造前 | 改造后 |
|---|---|---|
| DLPF 群延迟 | ~2.9 ms | ~1.9 ms |
| 采样等待（半周期） | 5 ms | 2.5 ms |
| I2C 读取 | ~25 ms（MPU 17 + HMC 8） | ~1.2 ms |
| 采样循环周期 | ~26 ms（≈38 Hz） | ~2 ms（≈400 Hz） |
| 串口发送（半周期） | 10 ms | 5 ms |
| 蓝牙 SPP | 20~40 ms | 20~40 ms |
| 上位机渲染 | 16~33 ms | 16~33 ms |
| **合计** | **~90~120 ms** | **~40~60 ms** |

延迟降了一半以上，而且降掉的部分全是**确定性**的（可估算、可复现）；
剩下的两大块（蓝牙、渲染）都不在固件可控范围内。

## 5. 代价与风险

| 改动 | 代价 | 出问题怎么退 |
|---|---|---|
| I2C 2 µs 半周期 | 对飞线、上拉电阻敏感 | `I2C_DELAY_US` 改回 4~6 |
| DLPF 94 → 184 Hz | 陀螺噪声变大，波形毛刺更明显 | `MPU6050_CONFIG` 改回 `0x02` |
| 采样 100 → 200 Hz | 每 5 ms 采一次，I2C 占用翻倍 | `SMPLRT_DIV` 改回 `0x09` |
| 姿态帧 50 → 100 Hz | 带宽占用 +0.6 kB/s | `ANO_TICK_DIV` 改为 2 |
| 磁力计 1/4 频率 | 航向更新变慢（本来只有 15 Hz） | 改 `s_hmc_div` 的门限 |

退化现象很明确：**如果 3D 完全不动或数据全 0**，先怀疑 I2C 太快导致 NAK，
把 `I2C_DELAY_US` 退回 4 再试；**如果数值有但抖动变大**，那是 DLPF 放宽的正常代价。

## 6. 还能做什么（本次未做）

| 方向 | 预期收益 | 代价 |
|---|---|---|
| 换 USB-TTL 直连 | 去掉 20~40 ms 蓝牙延迟 | 几块钱，插根线 |
| UART DMA + 空闲中断 | 发送不再阻塞任务，排队更短 | 需要改发送层与中断 |
| 硬件 I2C（400 kHz ~1 MHz） | I2C 从 1 ms 降到 0.3 ms | 要重写总线层，收益已不大 |
| 提高上位机渲染帧率 | 33 → 16 ms | 由上位机决定，固件管不着 |

按目前的延迟分布，**下一个该动的不是固件，是那条蓝牙**。
50 ms 的链路里，固件部分约占 10 ms（DLPF 1.9 + 采样 2.5 + I2C 1.2 + 串口 5）。

## 7. 想把延迟测准怎么办

本文的数字都是时序推算。要拿到真实值，最省事的办法是**用一根 GPIO 做标记**：

```c
/* 采样开始时拉高，姿态帧发完后拉低 */
HAL_GPIO_WritePin(GPIOA, GPIO_PIN_8, GPIO_PIN_SET);
...
HAL_GPIO_WritePin(GPIOA, GPIO_PIN_8, GPIO_PIN_RESET);
```

用示波器或逻辑分析仪看这个引脚的高电平宽度和周期，就能得到
「采样耗时」和「采样周期」的真实值，比任何估算都准。

没有仪器时，退一步的做法是数带宽：上位机 `接收计数` 每秒增长多少字节，
除以每帧字节数，反推实际帧率——能确认 100 Hz 有没有真的发出来。
