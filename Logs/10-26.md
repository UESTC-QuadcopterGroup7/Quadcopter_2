## 三、真正的问题（按优先级）

### 🔴 P0：I2C 逐字节读，导致更新率只有约 40 Hz + 数据撕裂

这是唯一一条会直接毁掉解算数据质量的。

**时序估算**（从 [MyI2C.c:10-25](Quadcopter_2/MyLib/MyI2C.c#L10-L25) 推的）：

```
每个 bit = W_SDA(10µs) + W_SCL(1)(10µs) + W_SCL(0)(10µs) = 30 µs
每个字节 = 240 µs + ACK 40 µs
单次 MPU6050_ReadReg = start+addr+reg+restart+addr+数据+stop ≈ 1.2 ms
```

[MPU6050_GetData()](Quadcopter_2/MyLib/GY86.c#L151-L174) 调 **12 次** `ReadReg` ≈ **14.6 ms**，[HMC5883L_GetData()](Quadcopter_2/MyLib/GY86.c#L231-L242) 调 **6 次** ≈ **7.3 ms**。一轮采集 ≈ **22 ms**，加 1 ms 延时 → **约 23 ms / 43 Hz**。

而 [Attitude_Quaternion.md:237](Quadcopter_2/Docs/Attitude_Quaternion.md#L237) 写的是"实际周期通常在 10ms 量级，正好和 100Hz 对齐"——**这条需要实测修正**，否则后面调 β 会全部基于错误的假设。

由此带来三个后果：

1. **高低字节撕裂**：同一个轴的 H 和 L 相隔 1.2 ms 分两次读，MPU 输出率 100 Hz（10 ms），每组 H/L 约 12% 概率跨越一次更新；6 个轴 → 每轮有 **50% 以上**概率至少一个轴错位。一旦某个轴的读数正好停在 256 计数进位边界附近（6 个轴里出现这种情况很正常），就会出现 **±256 计数的整字节错位 = 陀螺 ±15.6 °/s、加速度 ±0.125 g**。表现出来就是"姿态偶尔跳一下"，很容易被误判成"β 太大"。
2. **加速度和陀螺不是同一时刻的样本**：读完六轴要跨 15 ms。
3. **HMC5883L 必须一次连续读完 6 个数据寄存器**。参考仓库的注释说得很明确（[IMU.c:172](senior-repo/Project/APP_FUNC/IMU.c#L172)：`必须连续读完这六个数据，否则会导致隔很长一段时间才出新数据`）。你现在是 3 次独立事务，横滚时机体在动，X/Y/Z 就是从 3 个不同时刻采的，倾斜补偿直接算错。

**改法（参考仓库就是这么做的）**：MPU6050 从 `0x3B` 一次 burst 读完 14 字节（[IMU.c:155](senior-repo/Project/APP_FUNC/IMU.c#L155)），HMC 从 `0x03` 一次读 6 字节（[IMU.c:172](senior-repo/Project/APP_FUNC/IMU.c#L172)）。改完一轮 ≈ **4 ms + 1.9 ms ≈ 7 ms**，能跑到 100 Hz 以上，正好和 MPU 的 100 Hz 输出对齐，撕裂概率降到 1/4 以下。再把位延时从 10 µs 降到 2~3 µs（把 I²C 提到 150~250 kHz），一轮还能压到 1.5 ms 左右。

### 🟠 P1：dt 只有 1 ms 分辨率

[ReadPeripherals.c:184](Quadcopter_2/MyLib/ReadPeripherals.c#L184) 用 `HAL_GetTick()` 取差。在 23 ms 周期下量化误差约 **±4.3%**，而且这个误差是周期性相关的，会等效成航向比例误差持续累积。

`HAL_GetTick()` 本身能工作（[stm32f4xx_it.c:12-19](Quadcopter_2/Src/stm32f4xx_it.c#L12-L19) 里 `HAL_IncTick()` 和 `OS_CPU_SysTickHandler()` 都调了，`OS_TICKS_PER_SEC=1000` 正好 1 ms），所以不是 bug，只是精度不够。

建议改用 `DWT->CYCCNT`（需置 `DEMCR.TRCENA`，84 MHz 下 51 s 才回绕）。**注意不要用 TIM5**——它已经被 [Delay.c](Quadcopter_2/MyLib/Delay.c#L4-L28) 的 `Timer_Delay_us()` 占用（TIM2/TIM4 给输入捕获、TIM3 给 BLDC PWM，只剩 TIM6/TIM7 或 DWT）。

### 🟠 P1：磁力计的物理层没验证

1. **轴向映射**：代码按"HMC 与 MPU 同轴"处理（[ReadPeripherals.c:159-169](Quadcopter_2/MyLib/ReadPeripherals.c#L159-L169)，注释里自己也标了"以实物为准"）。参考仓库的实测记录 [九轴数据变化.txt](senior-repo/docs/九轴数据变化.txt) 写的是 **x 轴对应 pitch、y 轴对应 roll**——这说明这块板子上芯片轴和"X 机头 / Y 左翼"不一定一致，必须自己实测。
2. **没有硬铁/软铁校准**：航向有固定偏差，电机一转让电流干扰后 yaw 会乱跳。
3. **`Attitude_InitRaw()` 少了磁场门限**：[Attitude.c:215-237](Quadcopter_2/MyLib/Attitude.c#L215-L237) 只检查 `mag != 0`，没有像 [UpdateRaw:371](Quadcopter_2/MyLib/Attitude.c#L371) 那样用 `ATTITUDE_MAG_MIN_LSB` 过滤。如果上电时 HMC 读回全 `0xFF`（= -1,-1,-1，模长 1.73 < 100），初始航向会被设成约 **-135°**。而 [Attitude_Quaternion.md:258-259](Quadcopter_2/Docs/Attitude_Quaternion.md#L258-L259) 声称"代码用该门限把这种无效向量挡掉"——这个说法在初始化路径上不成立。
